# PR 04 - cuMem Sleep, Wake, And ROCm Teardown

## Reviewer Summary

This PR fixes the `test_sleep_mode` failure by changing the cuMem allocator,
not by shrinking the integration test. The important hypothesis is that MI300
was not out of physical memory: the preceding server reported GPU memory back
at baseline, and the failing allocation happened inside the cuMem allocator
while ROCm still reported almost all VRAM free. That makes ROCm virtual-address
reservation and custom MemPool teardown the likely root cause.

## What Changed

- ROCm VA reservation retries with default alignment when explicit alignment
  reports OOM.
- ROCm sleep now releases physical handles and cycles the VA reservation so
  memory becomes reusable while pointer identity is preserved for wake-up.
- If cycling the VA cannot restore the original address, the C++ code aborts
  rather than returning to Python with tracked tensors pointing at freed VA.
- The allocator tracks whether an allocation is currently mapped. If `wake_up`
  fails after `sleep`, teardown releases only the VA reservation instead of
  trying to unmap stale physical handles.
- The C++ callback accepts `None` from Python as a VA-only free signal.
- GIL release and Python error printing are fixed on callback error paths.
- ROCm uses lower-level MemPool begin/end allocation routing instead of the
  public `torch.cuda.memory.use_mem_pool()` context. The public context calls
  `_cuda_releasePool()` on exit; on the tested HIP stack, later MemPool
  teardown can abort after that release.
- ROCm cuMem tests use `spawn` instead of `fork`, because forking after HIP
  initialization is unsafe.

## Why `tests/basic_correctness/test_cumem.py` Changes Are Included

The API server failure was in `test_sleep_mode`, but `test_cumem.py` is the
allocator's focused coverage. It needs to exercise the exact failure classes:

- sleep releases memory and wake remaps it;
- expected wake OOM does not leave stale mapped-state behind;
- process teardown runs normally after allocator tests pass.

Those tests are not masking the integration failure. They are the unit-level
guard that makes the integration failure debuggable.

## Reviewer Questions We Must Answer

- Why is the `None` callback path global? Because `my_free()` has one callback
  ABI. CUDA still returns the 4-tuple in normal operation; `None` is inert
  unless Python says the handle is already unmapped.
- Why not use fast process exit? Because that hides teardown bugs. This patch
  keeps normal Python/PyTorch teardown active.
- Why are there test knobs for ROCm? They scope allocator unit tests so they
  test sleep/wake state rather than reserving most of a 192 GiB GPU for KV
  cache. The real API server sleep test remains the integration guard.
