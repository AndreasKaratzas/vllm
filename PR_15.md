# PR 15 - Tokenizer, Processor, Registry, And Model Discovery Hygiene

## Reviewer Summary

This PR collects import/setup hygiene. It is broad, so reviewers will need each
file tied to either a failing collect/import log or a specific model setup
failure. Tokenizer and processor changes can affect many models, so avoid vague
"stability" language.

## Why These Changes Exist

The changed files point at three categories:

- test registry policy for models that are unavailable, renamed, gated, or
  flaky on ROCm;
- tokenizer fallback behavior, including Hugging Face edge cases;
- processor/config setup for multimodal and transformer model initialization.

These categories should probably become separate PRs if any runtime tokenizer
behavior changes are substantial.

## Reviewer Questions We Must Answer

- Which model IDs failed before the patch, and why?
- Are registry changes test-only, or do they affect runtime model discovery?
- Does tokenizer fallback change user-visible tokenization?
- Are processor changes specific to ROCm, or general correctness fixes?

## Validation Commands

- Collect-only for `tests/models`.
- Focused initialization tests for each model ID whose registry entry changed.
- One tokenizer regression test for the `hf.py` change.
- `Multi-Modal Processor (CPU) %N` shard run if processor code remains changed.

## Weak Confidence

- Marking a model unavailable is weak unless the PR links the exact upstream
  model/revision problem.
- Tokenizer behavior changes are broad and should have direct tests.
