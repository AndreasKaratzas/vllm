# PR 06 - Quantization, ModelOpt, torchao, And Reload Gates

## Reviewer Summary

This PR should separate true runtime quantization fixes from test gating for
unsupported hardware. The strongest parts are MI250 capability gates for FP8,
FP4, and AITER-dependent paths. The risky parts are generic ROCm skips or dtype
changes that could hide MI300/MI325 regressions.

## Failure Basis

- MI250 was running tests that require FP8/FP4/AITER-style support it does not
  provide.
- ModelOpt FP8 per-channel/per-token checkpoints failed on ROCm due to float8
  format mismatch, for example `float8_e4m3fn` versus ROCm's expected
  `float8_e4m3fnuz`.
- Some reload tests were exercising quantization paths that are meaningful on
  MI300/MI325 but not MI250.

## Reviewer Questions We Must Answer

- Is each skip keyed to capability (`has_fp8`, architecture, AITER availability)
  rather than `is_rocm()`?
- Does MI300 still execute ModelOpt FP8 coverage after MI250 is gated?
- Are NVFP4 tests excluded from MI300 unless there is an AMD-supported path?
- Are runtime dtype changes covered by a numerical correctness test?

## Validation Commands

- Run `Model Executor` on MI250 collect-only and confirm unsupported FP8/FP4
  cases are skipped with explicit reasons.
- Run `Quantization` on MI300 for the ModelOpt FP8 setup case.
- Run `Quantized Models Test` on MI300/MI325 to ensure capability gates did not
  remove supported coverage.

## Weak Confidence

- Any test change that says "skip on ROCm" is weak unless the failure is truly
  all ROCm architectures.
