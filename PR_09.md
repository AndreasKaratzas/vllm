# PR 09 - DeepEP, OCP, GPT-OSS, And MoE Harness Gates

## Reviewer Summary

This PR should be about MoE test harness correctness and capability gates, not
new kernel feature work. It is tied to the user's request to install/check ROCm
external libraries such as DeepEP/NIXL/UCX before deciding whether a skip is
legitimate.

## Failure Basis

- DeepEP tests were initially unverifiable locally because
  `has_deep_ep() == false`. That is not enough to skip the test permanently;
  the ROCm external libraries from the Dockerfile must be present first.
- GPT-OSS and MXFP4/MXFP8 paths need architecture-specific handling. MXFP4
  should not be evaluated on MI300 just because it is part of a shared test
  matrix if the supported target is MI355.
- LoRA TP failures involving GPT-OSS/MoE should not be conflated with generic
  LoRA failures.

## Reviewer Questions We Must Answer

- Were DeepEP/NIXL/UCX dependencies installed before deciding a test is skipped?
- Which architectures support each FP8/FP4/MX format?
- Does MI300 still execute the MoE tests it can support?
- Are MI355 AITER accuracy problems gated to MI355 only?

## Validation Commands

- Run `Kernels FP8 MoE Test (2xH100-2xMI300)` after installing ROCm external
  libraries.
- Run focused GPT-OSS LoRA TP tests on MI300.
- Run collect-only on MI250 to confirm unsupported cases skip explicitly.

## Weak Confidence

- DeepEP skips are weak unless the PR shows the dependency is unavailable even
  after the ROCm Dockerfile external libraries are installed.
- Any MXFP4 skip must name the unsupported architecture.
