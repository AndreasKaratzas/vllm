# PR 08 - DeepSeek V4 Norm-Router GEMM

## Reviewer Summary

This is not a normal ROCm CI stabilization PR as currently shaped. It adds a
new CUDA-only fused RMSNorm + router GEMV path for DeepSeek V4 Pro, wires it
through the custom op registry, and adds a benchmark. That can be valuable
runtime work, but reviewers should not be asked to infer that it fixes an AMD
Buildkite failure unless we attach a specific failing command and before/after
data.

My recommendation is to split this out of the ROCm CI patch unless we can prove
that one of the MI300/MI325 failures is blocked by this exact dispatch path.

## Exact AMD Labels

No exact label in `.buildkite/test-amd.yaml` names this feature. The closest
labels that could exercise adjacent MoE/router code are:

- `Kernels MoE Test %N`
- `Kernels FP8 MoE Test (2xH100-2xMI300)`
- `Qwen3-30B-A3B-FP8-block Accuracy (4xH100-4xMI300)`

path for SM90+ and is not a direct MI300 ROCm kernel.

## What Changed

- Adds a new `_moe_C.dsv4_norm_router_gemm` op.
- Adds a Python wrapper `ops.dsv4_norm_router_gemm`.
- Adds `NormGateLinear`, a pluggable layer that can dispatch to the fused op
  for the DeepSeek V4 Pro shape.
- Adds CUDA sources for fused RMSNorm plus router GEMV:
  `x -> normed_x` and `normed_x @ gate_weight.T -> router_logits`.
- Registers the new source files in CMake using the same architecture gate as
  the existing DSV3 router GEMM path.
- Changes DSV3 router GEMM PDL behavior from always-on to controlled by
  `TRTLLM_ENABLE_PDL`.
- Adds an MXFP8 emulation path in `fused_moe/utils.py`; this is related MoE
  harness work but should probably be reviewed separately from the new DSV4
  CUDA kernel.

## Basis For The New Files

The new DSV4 files are not written from scratch in isolation. They are derived
from the existing DSV3 router GEMM implementation already in this repository:

- `csrc/moe/dsv3_router_gemm_entry.cu`
- `csrc/moe/dsv3_router_gemm_float_out.cu`
- `csrc/moe/dsv3_router_gemm_utils.h`

The DSV3 files themselves point at TensorRT-LLM DSV3 router GEMM sources. The
new DSV4 kernel keeps the same general low-latency structure: fixed small token
count, warp butterfly reduction, shared-memory cross-warp reduction, fp32
accumulation, 128-thread block, and SM90+ architecture gating. The DSV4-specific
part is folding RMSNorm into the router GEMV via:

```text
logits[m,n] = rsqrt(mean(x[m]^2) + eps)
              * sum_k(x[m,k] * norm_weight[k] * gate_weight[n,k])
```

That identity lets the kernel produce fp32 router logits while also writing the
bf16 normalized activation row needed by downstream experts.

## Why This Might Be Needed

This is plausible if DeepSeek V4 Pro routing is a runtime hotspot and the
unfused RMSNorm + router GEMM sequence is too slow for small decode batches.
The shape restrictions in the entrypoint are narrow:

- `hidden_dim == 7168`
- `num_experts == 384`
- `num_tokens in [1, 16]`
- bf16 inputs/weights
- fp32 logits
- SM90 through SM103

That narrowness is good for performance work but makes the change look like a
model-specific optimization, not a general CI repair.

## Reviewer Questions We Must Answer

- Which failing Buildkite job requires this path?
- Is the target model DeepSeek V4 Pro specifically, and are DSV4 Flash or other
  hidden sizes intentionally excluded?
- Why is the PDL change for existing DSV3 kernels bundled with the new DSV4
  kernel?
- Should the MXFP8 emulation change in `fused_moe/utils.py` move to PR 09 or PR
  06 instead?
- Is the new op CUDA-only by design? If yes, this should not be sold as an AMD
  ROCm CI fix.

## Required Benchmark Evidence

Before posting this as a runtime PR, collect at least:

- Correctness versus unfused `rms_norm + dsv3_router_gemm` for token counts
  `1, 2, 4, 8, 16`.
- Max absolute and relative error for `normed_x` and fp32 logits.
- Latency before/after on the target NVIDIA architecture, likely H100/H200/B200.
- A sweep with `TRTLLM_ENABLE_PDL=0` and `TRTLLM_ENABLE_PDL=1`, because this
  patch changes existing DSV3 PDL behavior too.
- Import/registration smoke:
  `python -c "import vllm._custom_ops as ops; print(hasattr(ops, 'dsv4_norm_router_gemm'))"`

## Validation Commands

- Focused correctness test for `dsv4_norm_router_gemm` against the unfused

- Build with CUDA SM90+ enabled and confirm `_moe_C` exports the op.

## Split Recommendation

Do not include this in the main ROCm CI stabilization stack unless a failing log
proves it is required. If kept, make it a separate performance PR with benchmark
tables and correctness tolerances.
